## 先制作什么

1. 综合门诊外观作为建筑代表样件：使用独立斜视图和门诊实景核对，俯视图锁定弧形。Tripo只提交单体候选；生成后的屋顶、幕墙和内部不得假定已自动拆开。
2. 一组候诊椅作为配套代表样件。确认细节、背面、支脚、贴图可用后，替换现有示意座椅并复用。
3. 单体样片通过后再处理急诊、停车楼。儿童医院和住院区目前按业务楼群拆出，后续每栋单独准备图，不将多个楼栋拼图整体生成。
4. 医技与连接裙房分别修整，按接口装回。道路、院区布局、楼层板、交互定位面继续由Blender控制，避免生成结果破坏空间关系。

## 输入资料的使用边界

- `front-three-quarter.png` 等是当前模型结构参考，保持同一对象的视图一致性，不是精细度目标。现有简化细节不应原样成为最终资产。
- 门诊俯视曲线以当前已校正模型和入口近景实照双重核对。不要仅用“向外/向内”文字判断，禁止镜像翻转。
- 用户提供的整院效果图只用来核对装配与外观氛围；不得直接把含多栋楼、树木和道路的整图交给Tripo生成一个不可拆院区。
- 1F/2F及候诊/接诊区为示意，非医院真实内部。zone_bindings是交互面，不作为有形建筑生成。floor_roof是展开模式替代屋顶，不能与门诊整体外壳同时叠加显示。
- environment包含按材质合并的树木、道路、铺地与CampusLife人车，属于装配参照，尚非逐棵/逐车语义拆分；替换道具需按现有位置重装配。不得把材质分块误认为独立单体。

## Tripo 接入后

队列文件是业务草案，不是某版本API请求体。接入时核实账号、额度、版本、支持的多视图/文本输入、导出能力与许可。先提交一个建筑样件，记录任务ID；超时查询原任务，禁止盲目重复付费。原始模型与贴图另存，Blender MCP负责修整、分件、校准、材质整理及GLB导出；网页视觉和交互验证后才替换当前资产。依用户约定，本轮没有性能测试。

## 验收约束

建筑轮廓、弧形、层数节奏、连廊接口先于贴图精细度。保留 objectId、floorId、zoneId 与现有前端绑定；日夜切换要能独立控制窗光，不能烘死夜景。检查屋檐薄面、背面、玻璃法线、UV、纹理路径与装配碰撞。接入前仍需单体精修参考，不承诺当前结构渲染直接送生成即可达到效果图品质。

查看 `index.html` 可浏览拆件和门诊四视图；实际提交记录统一保存在 `generation-queue.json`，当前 task_id 均为空。
